# 44 队列信号量互斥锁与任务通知

[返回总目录](../../README.md) · ESP32-D0WD / 4 MB Flash / ESP-IDF 6.1。

## 根据语义选择工具

队列传数据；二值信号量表达可等待事件；计数信号量表示资源数量；互斥锁保护共享资源；任务通知适合唤醒已知任务。选择工具应基于业务需求，而不是哪个API看起来更熟悉。

本例队列按sizeof(sample_t)复制结构体，生产者局部变量离开本轮后，消费者仍有独立副本。如果队列只复制指针，目标内存必须继续有效，并明确谁释放。发送栈上数组地址后立即复用，是常见生命周期错误。

## 容量与背压

令生产速率λ、消费速率μ。持续λ大于μ时，任何有限队列最终都会满；队列不能创造处理能力。每秒10条、服务暂停0.5秒、初始积压为零时，至少需要5项缓冲，还要预留启动相位和抖动余量。

示例满时立即失败并丢弃最新消息；另一种策略是有限等待，把压力传回生产者。显示最新温度可以用长度1的覆盖队列；控制命令、审计记录等则不能随意丢弃，应有确认、限流或持久化。动态数组无限增长只会把“队列满”延后变成堆耗尽。

发送失败必须检查。如果发送的是动态对象指针，失败后发送方仍负责回收；成功后是否转移所有权也必须事先约定。

## 互斥和优先级反转

低优先级任务持锁，高优先级任务等待锁，中优先级任务不断抢占持锁者，可能延长高优先级等待，这叫优先级反转。互斥锁的优先级继承可缓解，但不能使长时间持锁变得合理。

锁内只做必要的短操作，例如复制配置后解锁，再发网络请求。不要持锁等待一个必须获取同一锁才能产生的事件。多把锁固定获取顺序，减少循环等待。

volatile不能把count++这样的读改写变成原子，也不能代替跨核内存同步。共享数据需要合适的锁、原子操作或所有权设计。若一个任务独占I²C设备，其他任务用消息请求，通常比到处共享句柄更容易检查。

## 中断与任务通知

ISR使用允许的FromISR接口，不能阻塞等待队列空间。记录higher_priority_task_woken并按接口要求触发调度；队列满时选择丢弃、计数或硬件流控，不能在中断里无限重试。

任务通知开销较小，适合单个已知消费者。需要保存每个不同负载或多个消费者时，队列通常更清晰。二值事件可能合并多次发生，如果每次脉冲都必须计数，应使用计数机制或硬件计数器。

## 大缓冲的所有权

固定缓冲池可避免频繁申请和碎片化，流程为申请、填写、提交、消费、归还。发送成功后生产者不得修改已转移缓冲，消费者处理完成再归还。初学阶段先用小结构体按值传递，再学习零拷贝设计。

## 验收与练习

分别测试正常负载、队列满、消费者暂停和恢复。系统不能永久卡住，错误应有计数或日志。记录最大积压、丢失数与恢复时间，不只统计成功消息。

练习：在消息中增加16字节标签，比较按值与指针。参考：按值增加固定内存但生命周期简单；指针需要缓冲池、失败回收和有效期约定，不能只换一个字段类型。

## 完整工程与运行

[源码](../../examples/esp-idf/tasks_queue/main/main.c)，[构建配置](../../examples/esp-idf/tasks_queue/CMakeLists.txt)。先激活IDF 6.1，从手册根目录运行。

Windows PowerShell：

```powershell
Set-Location examples/esp-idf/tasks_queue
idf.py set-target esp32
idf.py build
$port = Read-Host '输入实际串口'
idf.py -p $port flash monitor
```

Linux Bash：

```bash
cd examples/esp-idf/tasks_queue
idf.py set-target esp32
idf.py build
read -r -p '输入实际串口: ' port
idf.py -p "$port" flash monitor
```

首次配置目标即可，已有配置先备份。退出monitor使用Ctrl+]。编译不要求接板，真实时序与波形需要硬件；[验证记录](../../validation/)列明已完成检查。前置：第40–42章；下一步按总目录继续。资料基线2026-10-29，教学代码为原创。
